These microbenchmarks isolate individual components. ProxyHandler uses `b.RunParallel` to measure concurrent throughput; the others run sequentially.

### How to Read These Numbers

- **ops/sec**: Higher is better. Derived from `1e9 / ns_per_op`.
- **ns/op**: Nanoseconds per operation. Lower is better.
- **B/op**: Bytes allocated per operation. Lower means less GC pressure.
- **allocs/op**: Heap allocations per operation. Lower means less GC pressure.

### Sources and Methodology Notes

1. **Kong:** Performance data from [Kong Performance Benchmark](https://docs.konghq.com/gateway/latest/production/performance/performance-benchmarks/) documentation. Tested on AWS c5.4xlarge with a simple passthrough proxy configuration. Results vary with plugin chain complexity.

2. **KrakenD:** Performance data from [KrakenD Benchmarks](https://www.krakend.io/docs/benchmarks/overview/) page. Tested with their standard benchmark suite on comparable hardware. KrakenD's stateless architecture (no database) reduces overhead compared to gateways backed by a data store.

3. **Apache APISIX:** Performance data from [APISIX Performance](https://apisix.apache.org/docs/apisix/benchmark/) documentation. Tested on AWS instances with etcd as the configuration store.

### Context for FlexGateway

FlexGateway uses PostgreSQL as its configuration store, which adds overhead compared to stateless gateways (KrakenD) or in-memory stores (APISIX/etcd). The tradeoff is richer configuration management and relational queries. Performance targets (10K RPS, p99 < 50ms) reflect a different design point than raw throughput maximization.
